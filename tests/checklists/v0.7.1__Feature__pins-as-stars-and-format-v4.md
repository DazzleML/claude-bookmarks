# Human Test Checklist: pins become stars (register format v4) and "Pins shown in a list"

**Target version:** 0.7.1
**Ships with commit:** `feat(bookmarks): pins become stars that remember their list; register format v4 (v0.7.1)` (subject may change at review)
**Companion automated tests:**
- core (`node --test tests/core/*.test.ts`), 537 in all, of which `tests/core/stars.test.ts` holds 15: stars, the scope, the union, the v3-to-v4 step, the read bridge;
- `tests/core/migrations.test.ts` and `tests/core/register-file.test.ts`, updated for v4;
- kit (`claude plugin test plugin`), 158 in all: `plugin/tests/stars.test.ts` (3: `*2` writes a star from the prompts list; `here` hides a star made elsewhere; `everywhere` shows it), and `plugin/tests/migration.test.ts` (the start-up migration now ends at v4).

## What this is

0.7.1 changes the bookmark file's format. A pin used to be a uuid in the file's `pins` list. Now it is a **star record** that also says which list it was made in (`from`) and when (`at`), and an `off` time when it is turned off. Every older file is migrated once, at a session's start, with a backup. On screen nothing is renamed: the prompts list still says "pin" and draws `★`. A new setting, **"Pins shown in a list"**, chooses whether a list shows only its own pins or every pin on its rows.

This checklist is for the person who maintains the plugin, run once on each machine that has bookmarks. Most of it is a look at files and at the prompts pane.

## Legend

| Term | Meaning |
|---|---|
| register | the per-conversation bookmark file, `<data root>/bookmarks/sessions/<session id>.json` |
| data root | `CLAUDE_USER_DIR` when it is set, else `<home>/claude` |
| v3 / v4 | the register's `version` (and `format`) field: v3 kept pins as `pins`, v4 as `stars` |
| run folder | one migration's backup folder under `<data root>/bookmarks/backups/`, named `<stamp>__v3-to-v4__<writer>__<first 8 of the session id>/` |
| read bridge | in a session that got 0.7.1 by a reload and has not started since, a v3 file shows its pins through the migration's own step, without writing |

## Prerequisites

1. Claude Code with the plugin at 0.7.1 (`/bm-env` names the version).
2. **Do the live sections on a copy unless the machine has not migrated yet.** A machine that already ran 0.7.1 has nothing at v3 left. To re-run the migration, copy a v3 original out of a run folder into a scratch data root, and point a fresh session at it with `CLAUDE_USER_DIR`. Never edit the real folder for this checklist.

   Scratch setup (pick your shell). `<RUN>` is one run folder's name and `<SID>` its session id:

   **cmd.exe**:
   ```cmd
   mkdir %TEMP%\bm-check-v4\claude\bookmarks\sessions
   copy "%USERPROFILE%\claude\bookmarks\backups\<RUN>\sessions\<SID>.json" %TEMP%\bm-check-v4\claude\bookmarks\sessions\
   set CLAUDE_USER_DIR=%TEMP%\bm-check-v4\claude
   claude
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\bm-check-v4\claude\bookmarks\sessions" | Out-Null
   Copy-Item "$env:USERPROFILE\claude\bookmarks\backups\<RUN>\sessions\<SID>.json" "$env:TEMP\bm-check-v4\claude\bookmarks\sessions\"
   $env:CLAUDE_USER_DIR = "$env:TEMP\bm-check-v4\claude"
   claude
   ```

   **POSIX**:
   ```bash
   mkdir -p /tmp/bm-check-v4/claude/bookmarks/sessions
   cp "$HOME/claude/bookmarks/backups/<RUN>/sessions/<SID>.json" /tmp/bm-check-v4/claude/bookmarks/sessions/
   export CLAUDE_USER_DIR=/tmp/bm-check-v4/claude
   claude
   ```

   Choose a run folder whose original has pins:

   **PowerShell**: `Select-String -Path "$env:USERPROFILE\claude\bookmarks\backups\*__v3-to-v4__*\sessions\*.json" -Pattern '"pins"' -List | Select-Object Path`

   **POSIX**: `grep -l '"pins"' "$HOME"/claude/bookmarks/backups/*__v3-to-v4__*/sessions/*.json`

   **cmd.exe**: `findstr /m /s "\"pins\"" "%USERPROFILE%\claude\bookmarks\backups\*.json"`

3. **Reset between sections:** delete the scratch folder and copy again.

## High-Value Verification (~5 minutes)

### HV.1: a v3 register becomes v4 at a session's start, with its pins as stars

Validates: the start-up migration on a real file.

- [ ] **Steps:** start a session on the scratch data root (Prerequisites, step 2), then open its register:
  - **PowerShell**: `Get-Content "$env:CLAUDE_USER_DIR\bookmarks\sessions\<SID>.json"`
  - **cmd.exe**: `type %CLAUDE_USER_DIR%\bookmarks\sessions\<SID>.json`
  - **POSIX**: `cat "$CLAUDE_USER_DIR/bookmarks/sessions/<SID>.json"`
- [ ] **Expected:**
  - `"version": 4` and `"format": 4` near the top;
  - no `"pins"` key;
  - a `"stars"` list with one entry per former pin, each with `"owner": "user"`, `"from": "prompts"` and an `"at"` time;
  - the bookmarks (`"perma"`) and the letters (`"slots"`) unchanged from the original.
- [ ] **Why this matters:** a pin lost here is lost from the person's list.

### HV.2: the backup is the v3 original

Validates: the run folder, written before the file is touched.

- [ ] **Steps:** list `<data root>/bookmarks/backups/` and open the new `__v3-to-v4__` folder's `manifest.json`, then compare its `sessions/<SID>.json` with the file you copied in.
- [ ] **Expected:** `"status": "done"`; `"from": 3`, `"to": 4`; the copy is byte-for-byte the v3 file (`fc /b` on cmd.exe, `Compare-Object (Get-Content a) (Get-Content b)` in PowerShell, `cmp a b` on POSIX).
- [ ] **Why this matters:** the backup is the only way back.

### HV.3: the prompts pane still shows the pins

Validates: pins read from stars.

- [ ] **Steps:** on your real data root (no `CLAUDE_USER_DIR`), in a conversation that had pins, press `Ctrl+] p`.
- [ ] **Expected:** the **★ pinned** group at the top, in the order you pinned them, and `N★)` in each pinned prompt's number in the full list.
- [ ] **Why this matters:** the migration is only right if the person sees the same pins as before.

### HV.4: pin and unpin after the migration

Validates: the star operation through every gesture.

- [ ] **Steps:** in the pane's field (`/bm-prompts` from an empty input box) type `*N` and Enter for an unpinned prompt; then again for the same one. Do the same from the band (`Ctrl+] p`, a number, `s`).
- [ ] **Expected:** the first toggle adds `★` and a toast "pinned #N"; the second removes it ("unpinned #N"). In the register, the star's entry gains an `"off"` time on unpin, and loses it (with a new `"at"`) on pinning again.
- [ ] **Why this matters:** an unpin that only hides would come back when two copies of the file meet.

### HV.5: the new setting

- [ ] **Steps:** `/config`, the Bookmarks fold.
- [ ] **Expected:** a row **"Pins shown in a list"** with `here` and `everywhere`, set to `here`. Setting `everywhere` changes nothing you can see yet: the prompts list is the only list so far, and every pin is made there. Set it back.
- [ ] **Why this matters:** a saved setting of a wrong type stops the plugin loading, so the row must load and save cleanly.

## Section 1: the folder as a whole

### 1.1 Every register migrates in one start

- [ ] **Steps:** copy two or more v3 originals (Prerequisites) into the scratch `sessions/`, start one session.
- [ ] **Expected:** every file is at v4 and each has its own run folder, from the one start. A file with an empty pins list (`"pins": {"user": []}`) becomes v4 with no `"stars"` key.

### 1.2 `/bm-check` after the migration

- [ ] **Steps:** `/bm-check`.
- [ ] **Expected:** "N register file(s) under bookmarks/sessions; N at v4" and no warning about the registers. It changes no file.

### 1.3 A second start does nothing

- [ ] **Steps:** close the session and start another on the same data root.
- [ ] **Expected:** no new run folder; the register's `rev` is unchanged.

## Section 2: across builds

### 2.1 An older build reads a v4 file and does not write it

Run only where an older build is installed (for example, a second machine not yet updated).

- [ ] **Steps:** with that build, open a conversation whose register is at v4; try to pin a prompt or to rename a bookmark.
- [ ] **Expected:** a toast once at load: "this conversation's bookmark file was written by a newer build ... it is read-only here until the plugin is updated"; the change is not saved, and the file is unchanged. Its pins do not show (that build reads only `pins`).

### 2.2 The second machine's first start on 0.7.1

- [ ] **Steps:** update the plugin there and start a session.
- [ ] **Expected:** HV.1 and HV.2 hold on that machine's own folder. Once this has happened on every machine, the read bridge can be removed (the maintainers' open loop).

### 2.3 The read bridge (only while a session has not restarted since the update)

- [ ] **Steps:** in a session that was open while the plugin updated, before starting a new one, open the prompts pane.
- [ ] **Expected:** pins still show from a file that is still at v3, and pinning or unpinning still works there; the file stays at v3 until the next start.

## What the automated tests DON'T cover

- The real start-up sweep over a real folder with real file sizes, timestamps and `.bak` files.
- The window after a reload and before a start (Section 2.3): the kit always starts a session.
- An older build on another machine meeting a v4 file (Section 2.1).
- The toast's wording and how long it stays.
- `/config`'s drawing of the new row.

## Reporting issues found

1. Note the section and step.
2. Keep the scratch folder as it is, and copy the run folder and the register.
3. File an issue naming this checklist and the version from `/bm-env`.

## Cleanup

Delete the scratch data root and unset `CLAUDE_USER_DIR`:

- **cmd.exe**: `rmdir /s /q %TEMP%\bm-check-v4` then `set CLAUDE_USER_DIR=`
- **PowerShell**: `Remove-Item -Recurse -Force "$env:TEMP\bm-check-v4"` then `Remove-Item Env:\CLAUDE_USER_DIR`
- **POSIX**: `rm -rf /tmp/bm-check-v4` then `unset CLAUDE_USER_DIR`

Your real `<home>/claude/bookmarks` is never touched by Sections 1 and 2.3 on a scratch root. HV.3 and HV.4 run on your real folder, and pinning there is an ordinary change you can undo by toggling again.
