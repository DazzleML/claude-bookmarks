# Human Test Checklist: Obsidian keeps a bundle file's block

**Target version:** 0.8.x, before the bundle file is built (it gates that unit)
**Ships with commit:** TBD (the checklist is written ahead of the code it gates)
**Companion automated tests:** none yet. The bundle file's parser and its tests are the unit this checklist gates. The format was proven on real bundles by a proof of concept: round trips, notes kept over three regenerations, torn reads refused.

## What this is

A bundle will be a Markdown file the plugin writes into a project's vault, which a person can open in Obsidian. The plugin owns the front matter's fixed fields, a fenced `bm-links` block holding the bundle's links as one line of JSON, and a `## Links` list it regenerates. The person owns everything below the notes marker. This checklist answers one question nothing but Obsidian can answer: **when a property is edited in Obsidian's Properties panel, does Obsidian leave the fenced block, and the rest of the body, untouched?**

It takes about two minutes, and every step is manual. If the block survives, the bundle file is built as designed. If it does not, the links move to a sidecar `<id>.json` beside the Markdown file, and the bundle file's unit changes before it is built.

## Prerequisites

1. Obsidian, with a vault open. Note **which folder the vault is opened on**: the folder that holds `.obsidian/`. Step HV.4 asks for it.
2. `git` on the PATH, for `git diff --no-index`, which compares any two files whether or not they are in a repository. On cmd.exe without git, `fc /N` works too.
3. **Never over a real file.** The sample goes into a new scratch folder inside the vault; nothing already there is touched.

**Set two names once** (pick your shell). `REPO` is this repository's folder; `VAULT` is the folder Obsidian has open.

**cmd.exe**:
```cmd
set REPO=C:\path\to\claude-bookmarks
set VAULT=C:\path\to\your\vault
mkdir "%VAULT%\bm-obsidian-test"
copy "%REPO%\tests\checklists\fixtures\sample-bundle.md" "%VAULT%\bm-obsidian-test\sample-bundle.md"
```

**PowerShell**:
```powershell
$env:REPO = "C:\path\to\claude-bookmarks"
$env:VAULT = "C:\path\to\your\vault"
New-Item -ItemType Directory "$env:VAULT\bm-obsidian-test" | Out-Null
Copy-Item "$env:REPO\tests\checklists\fixtures\sample-bundle.md" "$env:VAULT\bm-obsidian-test\sample-bundle.md"
```

**POSIX**:
```bash
export REPO=/path/to/claude-bookmarks
export VAULT=/path/to/your/vault
mkdir -p "$VAULT/bm-obsidian-test"
cp "$REPO/tests/checklists/fixtures/sample-bundle.md" "$VAULT/bm-obsidian-test/sample-bundle.md"
```

## High-Value Verification (~2 minutes)

These four steps are the whole test.

### HV.1 -- Edit two properties in Obsidian

Validates: Obsidian's Properties panel writes the front matter the way a person would edit it.

- [ ] **Steps:**
  1. In Obsidian, open `bm-obsidian-test/sample-bundle.md`.
  2. In the Properties panel at the top, change `why` to `edited in Obsidian`.
  3. Add a second tag, `bm/obsidian-test`.
  4. Close the note, or switch to another one, so Obsidian saves it.
- [ ] **Expected:** the note shows both edits, and the fenced `bm-links` block below the properties appears as a code block.
- [ ] **Why this matters:** a person, a skill or Obsidian may edit `label`, `why`, `tags` and `started`, and the plugin takes those edits. That only works if Obsidian writes them back where the plugin reads them.

### HV.2 -- Compare the file with the original

Validates: the fenced block, the Links list, the marker, the notes and the end line are byte-for-byte what they were.

- [ ] **Steps** (pick your shell):

  **cmd.exe**:
  ```cmd
  git diff --no-index --word-diff "%REPO%\tests\checklists\fixtures\sample-bundle.md" "%VAULT%\bm-obsidian-test\sample-bundle.md"
  ```
  (without git: `fc /N "%REPO%\tests\checklists\fixtures\sample-bundle.md" "%VAULT%\bm-obsidian-test\sample-bundle.md"`)

  **PowerShell**:
  ```powershell
  git diff --no-index --word-diff "$env:REPO\tests\checklists\fixtures\sample-bundle.md" "$env:VAULT\bm-obsidian-test\sample-bundle.md"
  ```

  **POSIX**:
  ```bash
  git diff --no-index --word-diff "$REPO/tests/checklists/fixtures/sample-bundle.md" "$VAULT/bm-obsidian-test/sample-bundle.md"
  ```
- [ ] **Expected (pass):** the only changes are inside the front matter: the `why` line, and one added line under `tags:`. Nothing changes below the closing `---`.
- [ ] **Fail if:** anything below the front matter changed. For example, the block was reflowed, re-indented or re-fenced, a blank line was added or removed, the `<!-- bm ... -->` lines changed, or the file's line endings changed throughout (the diff then shows every line).
- [ ] **Why this matters:** the plugin reads the bundle's links from that block. If Obsidian rewrites it, the links have to live outside the Markdown file.

### HV.3 -- Note how Obsidian wrote the front matter

Validates: what the plugin's front-matter reader has to accept.

- [ ] **Check, from the same diff,** whether Obsidian changed any line you did not edit:
  - quotes added around a value (`why: "edited in Obsidian"`);
  - the tags list rewritten in another form (`tags: [bm/sample, bm/obsidian-test]`);
  - a date reformatted (`2026-11-02T18:02:00Z` becoming `2026-11-02T18:02:00.000Z`, or a date only);
  - the key order changed.
- [ ] **Expected:** any of these is allowed. It is not a failure; it is information the reader is built from.
- [ ] **Why this matters:** the plugin regenerates the fixed fields and takes the editable ones. It has to read Obsidian's style as well as its own.

### HV.4 -- Report

- [ ] **Paste, back to the session that asked for this:**
  1. the diff output from HV.2;
  2. pass or fail for HV.2;
  3. anything HV.3 noticed;
  4. **the vault root**: the folder that holds `.obsidian/`.

## What the automated tests DO cover

| Area | Where | Count |
|---|---|---|
| The bundle file format on 27 real bundles (round trip, notes kept over three regenerations, every cut at each 1/64 of the file refused once the end line is required) | the bundles proof of concept (a one-off under `tests/one-offs/thinking/`) | 27 bundles, 1,701 cuts per sweep |
| The bundle file's parser and writer | the unit this checklist gates | not written yet |

## What the automated tests DON'T cover

- How Obsidian's Properties panel writes front matter. Only Obsidian can show it, and its style may change between Obsidian versions.
- Whether Obsidian, or a community plugin in the vault (a linter, a formatter), rewrites the body of a note it did not create.
- Line endings and trailing newlines as Obsidian saves them on this machine.
- Whether the code block renders readably in reading view.

## Reporting issues found

1. Note the step (HV.2 or HV.3).
2. Paste the exact diff.
3. Name the Obsidian version (Settings, About) and any community plugins that format notes.
4. Report it to the session that is building 0.8.x, or on issue #45.

## Cleanup

Remove the scratch folder with `dz safedel` (recoverable), or by hand if `dz` is not installed.

**cmd.exe / PowerShell / POSIX** (with `dz`):
```
dz safedel "<VAULT>/bm-obsidian-test"
```

Without `dz`: delete the `bm-obsidian-test` folder from the vault in your file manager, or from Obsidian's file pane. Nothing else was created.
