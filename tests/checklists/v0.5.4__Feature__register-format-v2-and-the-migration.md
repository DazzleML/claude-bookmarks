# Human Test Checklist: the register format v2 and its migration

**Target version:** 0.5.4
**Ships with commit:** `feat(register): format v2 with migrations, the snapshot and run folders (v0.5.4)`
**Companion automated tests:** 333 core tests under `tests/core/` (`migrations.test.ts` 7, `register-ops.test.ts` 10, `register-file.test.ts` 20 among them) and 89 kit tests under `plugin/tests/` (`migration.test.ts` 4, `guard.test.ts` 8), run with `node --test tests/core/*.test.ts` and `claude plugin test plugin`.

## What this is

The first release that changes what a bookmark file on disk contains, and the mechanism every later change uses: a numbered migration step, run when a conversation starts, with a backup first. The automated tests prove the steps on fixtures and the runner against a stubbed file system; this checklist is for the one thing they cannot touch, a real data folder with real history, and for what a person sees afterwards in the panes.

Run it once on a machine that has bookmarks from 0.4.x or 0.5.0-0.5.3. On a fresh machine there is nothing to migrate, and only HV.4 and Section 2 apply.

## Prerequisites

1. Claude Code 2.1.288 or later, the plugin at 0.5.4 or later (`/bm-env` shows the version), the fullscreen renderer (`/tui fullscreen`).
2. A data folder with at least one bookmark file from before 0.5.4: `~/claude/bookmarks/sessions/<session id>.json` whose first lines read `"version": 1` (or no `version` line at all). `CLAUDE_USER_DIR`, if set, replaces `~/claude`.
3. **Make your own copy first.** The migration takes its own snapshot, but a checklist run should never depend on the thing it is checking:

   **cmd.exe**:
   ```cmd
   xcopy /E /I "%USERPROFILE%\claude\bookmarks" "%TEMP%\bookmarks-before-0.5.4"
   ```
   **PowerShell**:
   ```powershell
   Copy-Item -Recurse "$env:USERPROFILE\claude\bookmarks" "$env:TEMP\bookmarks-before-0.5.4"
   ```
   **POSIX**:
   ```bash
   cp -r ~/claude/bookmarks /tmp/bookmarks-before-0.5.4
   ```
4. Note how many bookmark files you have (the `.json` files directly under `sessions/`, not the `.bak` ones) and how many conversations have pinned prompts (the `★` rows at the top of the prompts pane). On the author's machine on 2026-10-16: 5 files, 3 conversations with pins of which 2 had no bookmark file.

**Reset between sections:** none needed; every section reads. To re-run the migration itself, restore the copy from step 3 over `~/claude/bookmarks/` and delete `bookmarks/backups/` (your copy from step 3 is the recovery).

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these four. They are the "did the migration happen, and did it keep everything" tests.

### HV.1 -- The snapshot exists and holds everything that was there

Validates: the one interim copy is taken before the first migration writes anything.

- [ ] **Steps:**
  1. Start Claude Code (or reload the plugin) in any project. Wait for the band to appear.
  2. List the backups folder:

     **cmd.exe**: `dir "%USERPROFILE%\claude\bookmarks\backups"`
     **PowerShell**: `Get-ChildItem "$env:USERPROFILE\claude\bookmarks\backups"`
     **POSIX**: `ls ~/claude/bookmarks/backups`
- [ ] **Expected:** exactly one folder ending `__pre-0.5__snapshot`, named with the time of that start (`2026-10-16T21-55-00Z__pre-0.5__snapshot`). Inside: `manifest.json` and a `sessions/` folder that mirrors what `sessions/` held before (every `.json`, every `.json.bak`, every `<session id>/<uuid8>.md` export). Compare the file count with your copy from the prerequisites: they match.
- [ ] **Why this matters:** if the snapshot is missing or partial, the migration ran without the safety net the design promised.

### HV.2 -- One run folder per migrated file, each finished

Validates: every old file got its own backup folder and the status ladder reached `done`.

- [ ] **Steps:**
  1. In the same `backups/` listing, count the folders matching `*__v1-to-v2__*`.
  2. Open any one of them.
- [ ] **Expected:** one folder per bookmark file that was at version 1, plus one per conversation that had pins but no file. Each holds `manifest.json` with `"status": "done"`, `"from": 1`, `"to": 2`, a `files` list naming `sessions/<id>.json` (and `.json.bak` when one existed, and `store/<id>.json` when pins were moved) each with a hash, and those files beside it. The copied `sessions/<id>.json` is byte for byte the file as it was.
- [ ] **Why this matters:** a manifest left at `started` or `backed-up` means the run was interrupted and the live file may be half-written; a missing folder means a file was migrated without a backup.

### HV.3 -- Every live file is at version 2 and reads as before

Validates: the hoist and the numbering landed, and nothing a bookmark needs was lost.

- [ ] **Steps:**
  1. Open any `~/claude/bookmarks/sessions/<id>.json` in an editor.
  2. In Claude Code, in a conversation that had bookmarks, press `Ctrl+] b`.
- [ ] **Expected:** the file begins `"version": 2`, then `"sessionId"`, then one `"transcript"` line with forward slashes, then `"nextN"`; each entry under `"perma"` begins with `"n": 1`, `"n": 2`, ... in the order the bookmarks were made, and carries no `sessionId` or `transcript` of its own unless it was copied from another conversation. The bookmarks pane lists the same bookmarks as before the upgrade, and clicking one jumps as before.
- [ ] **Why this matters:** this is the format every later feature reads; a record that lost its transcript or its number here is wrong for good.

### HV.4 -- Pins survive and now live in the file

Validates: the move of pins out of Claude Code's store.

- [ ] **Steps:**
  1. In a conversation that had pinned prompts, press `Ctrl+] p`.
  2. Pin one more prompt (`*` then its number, or `s` on a picked row), then unpin it again.
  3. Look at that conversation's `.json` file.
- [ ] **Expected:** the `★` rows are the ones you had. The file holds `"pins": { "user": [ ...uuids... ] }`, and the list changes with each toggle (the file's `rev` goes up by one each time). The old store entry is gone: `~/.claude/plugins/store/bookmarks_inline-*.json` no longer has a `pins:<this session id>` key (read-only look; do not edit that file).
- [ ] **Why this matters:** pins are the first store-resident thing moved into the file; if the pane read one place and the toggle wrote another, pins would appear to vanish or double.

## Section 1: the migration's run (~5 minutes)

### 1.1 The debug log says what happened

- [ ] **Steps:** open `~/claude/bookmarks/debug/<session id>.log` for the conversation you started in (or `/bm-debug on` before the start and read the conversation).
- [ ] **Expected:** one line per migrated file, `[bm] migrate: <id8> v1 -> v2 (<N> record(s), pins moved from the store); run folder <name>`, a `[bm] migrate: snapshot of <N> file(s) under ...` line before the first of them, and a closing `[bm] migrate: <N> register(s) brought to version 2; originals under ...`.

### 1.2 A second start does nothing

- [ ] **Steps:** quit Claude Code; note the number of entries in `backups/`; start it again; list `backups/` again.
- [ ] **Expected:** the same entries, no new snapshot, no new run folder; no `migrate:` lines in the new debug log beyond none at all.

### 1.3 The old `.bak` beside each live file is the pre-migration original

- [ ] **Steps:** open `sessions/<id>.json.bak` for a migrated conversation.
- [ ] **Expected:** `"version": 1` (or no version line): the file as it was before the migration, identical to `backups/<run>/sessions/<id>.json`.

## Section 2: the format in use (~5 minutes)

### 2.1 A new bookmark is numbered and the file stays hoisted

- [ ] **Steps:** ask Claude to bookmark a line (or `/bm-promote a` on a mark). Open the file.
- [ ] **Expected:** the new record carries `"n": <nextN before>` and `nextN` is one higher; the record has no `transcript` of its own (the file's covers it); the link Claude wrote in its reply works as before.

### 2.2 A hand edit survives a save

- [ ] **Steps:** with the conversation open, edit a bookmark's `label` in the `.json` by hand and save the editor. Back in Claude Code, ask Claude to relabel a *different* bookmark.
- [ ] **Expected:** both changes are in the file: yours and Claude's. The debug log says `changed on disk ... the operation was applied to the disk's version`.

### 2.3 A fresh conversation gets a v2 file

- [ ] **Steps:** start a new conversation, make one bookmark, open its new `.json`.
- [ ] **Expected:** `"version": 2`, `"nextN": 2`, one record with `"n": 1`.

## What the automated tests DO cover

| Area | Test file | Count |
|---|---|---|
| the v1 -> v2 step: hoist, numbering, pins, determinism, store-only files, folder names, hashes | `tests/core/migrations.test.ts` | 7 |

## What the automated tests DON'T cover

- A real data folder with real history: files written by several past builds, `.bak` files that differ from their file, exports from before the register existed.
- `$.fs.list` and `$.fs.write` on a real disk (the kit stubs them): folder creation, a path with spaces, Windows path length.
- The deletion of the store key (`$.store.delete`): the kit's mock store does not report it; HV.4 is the only check.
- What the panes draw after the migration, and whether a jump from a migrated bookmark still lands.
- The plugin reloading mid-session (the migration then runs against a conversation already open).
- Time: how long a start takes with many files (5 here; a machine with hundreds is untried).

## Reporting issues found

1. Note the section and step number.
2. Attach the debug log of the start (`~/claude/bookmarks/debug/<session id>.log`) and the `manifest.json` of the run folder concerned.
3. Keep the `backups/` folder and your prerequisite copy; file an issue at https://github.com/DazzleML/claude-bookmarks/issues referencing this checklist and the version.

## Cleanup

Nothing to undo: the migration is the intended state. Your prerequisite copy under `%TEMP%` / `/tmp` can be deleted once HV.1-HV.4 pass. The `backups/` folder stays by design (it is the record, and the recovery, until a backup tool versions `~/claude`).
