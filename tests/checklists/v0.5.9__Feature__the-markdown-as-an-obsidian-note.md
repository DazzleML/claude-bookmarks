# Human Test Checklist: the Markdown as an Obsidian note

**Target version:** 0.5.9
**Ships with commit:** `feat(note): the Markdown export as an Obsidian note, edits read back (v0.5.9)`
**Companion automated tests:** 354 core tests under `tests/core/` (`note.test.ts` 5, `record.test.ts` 7, `register-file.test.ts` 12 among them) and 96 kit tests under `plugin/tests/` (`note.test.ts` 2, `guard.test.ts` 8), run with `node --test tests/core/*.test.ts` and `claude plugin test plugin`.

## What this is

From 0.5.9 each bookmark's Markdown file (`~/claude/bookmarks/sessions/<session>/<uuid8>.md`) is written as an Obsidian note: `tags` and `aliases` are YAML lists, the tags carry `bm/tier/...` and `bm/owner/...` for every record on the message, and three properties -- `label`, `why`, `tags` -- are read back from the note into the bookmark file the next time the plugin touches that bookmark. The automated tests prove the writer, the parser and the read-back against text the plugin itself wrote. They cannot open Obsidian. This checklist does: it is for the person with a vault, and it takes about ten minutes.

## Prerequisites

1. Claude Code with the plugin at 0.5.9 loaded (the band's `?` or `/bm-env` names the version), on a machine whose `~/claude/bookmarks/sessions/` already holds at least one conversation with a bookmark.
2. Obsidian installed (any recent version). You will point it at `~/claude/bookmarks` (or `$CLAUDE_USER_DIR/bookmarks`), as a new vault or a folder added to one. Nothing here changes an existing vault.
3. A conversation open in Claude Code with one bookmark of yours on a message (make one: a mark with `<leader> m a`, then `/bm-promote a`). Note its uuid8 from the toast or the bookmarks pane: `<u8>` below.
4. Before anything else, copy the conversation's bookmark file aside:

   **cmd.exe**: `copy "%USERPROFILE%\claude\bookmarks\sessions\<sid>.json" "%TEMP%\<sid>.before-0.5.9.json"`
   **PowerShell**: `Copy-Item "$env:USERPROFILE\claude\bookmarks\sessions\<sid>.json" "$env:TEMP\<sid>.before-0.5.9.json"`
   **POSIX**: `cp ~/claude/bookmarks/sessions/<sid>.json /tmp/<sid>.before-0.5.9.json`

Reset between sections: nothing destructive happens here; to undo an adopted edit, relabel the bookmark again from Claude Code (ask Claude to `relabel` it with the old label).

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these five. They cover what shipped.

### HV.1 -- The note is written in Obsidian's form

Validates: `exportMarkdown` (lists, derived tags, version 2).

- [ ] **Steps:** in Claude Code, ask Claude to relabel the bookmark (`relabel <u8>` with any `why`), or `/bm-promote` a letter again; then open the note:

  **cmd.exe**: `type "%USERPROFILE%\claude\bookmarks\sessions\<sid>\<u8>.md"`
  **PowerShell**: `Get-Content "$env:USERPROFILE\claude\bookmarks\sessions\<sid>\<u8>.md" -TotalCount 25`
  **POSIX**: `head -25 ~/claude/bookmarks/sessions/<sid>/<u8>.md`
- [ ] **Expected:** `version: 2`; `bm-writer:` ending `0.5.9`; `tags:` followed by indented `- ` lines, among them `- bm/tier/bookmark` and `- bm/owner/user`; no `tags: a, b` on one line. If Claude also has a record on that message, `owners: user, claude` and the derived tags of both.
- [ ] **Why this matters:** a comma-string `tags` is one tag to Obsidian; the list is what makes the vault's tag pane and search work.

### HV.2 -- Obsidian reads it

Validates: the YAML subset against Obsidian's own parser.

- [ ] **Steps:** open `~/claude/bookmarks` in Obsidian (Open folder as vault); open `sessions/<sid>/<u8>.md`; look at the Properties block at the top of the note (Reading or Live Preview view).
- [ ] **Expected:** `tags` shown as tag chips, `bm/tier/bookmark` among them; `aliases` as a list when the message is on both lists; `title`, `project`, `label`, `why` as text; no property shown in red (an unparsed value) and no "Invalid properties" notice. The tag pane (`Tags` view) lists `bm/tier/bookmark` and `bm/owner/user` with counts.
- [ ] **Why this matters:** the writer emits a YAML subset by hand; this is the only check that Obsidian agrees with it.

### HV.3 -- An edit in Obsidian is read back

Validates: `ingestNote` before the action, `ingest` against the base, the regenerated note.

- [ ] **Steps:** in Obsidian's Properties, change `label` to `renamed in Obsidian` and add a tag `vault-test`; save (Ctrl+S or just switch away). Back in Claude Code, ask Claude to `relabel <u8>` with a new `why` only (not a label). Then open the bookmarks pane (`<leader> b`) and the note again.
- [ ] **Expected:** the pane lists the bookmark as `renamed in Obsidian`; the bookmark file (`<sid>.json`) has `"label": "renamed in Obsidian"`, `"tags": ["vault-test"]` and no `bm/...` tag; the note is rewritten with `label: renamed in Obsidian`, the `why` Claude gave, `- vault-test` then the `bm/...` tags; the debug log (`/bm-debug on` beforehand, or the log file) has a line `note: <u8>.md edited by hand; adopted label, tags`.
- [ ] **Why this matters:** this is the feature: the register is the one source, and an edit in the vault reaches it rather than being overwritten.

### HV.4 -- An old note is not read back

Validates: the writer floor.

- [ ] **Steps:** pick a bookmark whose note was written before 0.5.9 (its `bm-writer` is missing or ends below `0.5.9`; any note written yesterday). In Obsidian change its `label`. In Claude Code relabel that bookmark's `why`.
- [ ] **Expected:** the label in the pane and the bookmark file is unchanged; the note is rewritten whole with the old label, now at `version: 2` with the list form; the log says `read back: the note's writer ... is below 0.5.9` (or `names no writer`). From here on the note is a 0.5.9 note and HV.3 applies to it.
- [ ] **Why this matters:** an old build's note has no base to compare against; reading it back would turn its stale text into an edit.

### HV.5 -- `.bak` is still the file before the action

Validates: the bookkeeping write (the note's base) does not rotate `.bak`.

- [ ] **Steps:** note the bookmark file's `"rev"`; relabel the bookmark from Claude Code; compare:

  **PowerShell**: `Select-String '"rev"|"label"' "$env:USERPROFILE\claude\bookmarks\sessions\<sid>.json", "$env:USERPROFILE\claude\bookmarks\sessions\<sid>.json.bak"`
  **POSIX**: `grep -n '"rev"\|"label"' ~/claude/bookmarks/sessions/<sid>.json ~/claude/bookmarks/sessions/<sid>.json.bak`
  **cmd.exe**: `findstr /n "\"rev\" \"label\"" "%USERPROFILE%\claude\bookmarks\sessions\<sid>.json" "%USERPROFILE%\claude\bookmarks\sessions\<sid>.json.bak"`
- [ ] **Expected:** `.bak` holds the label from *before* the relabel and the rev before it; the live file's rev is two higher (the relabel, then the base) and carries `"md": { "base": {...} }` on the record.
- [ ] **Why this matters:** `.bak` is the undo of your last action; a bookkeeping write that replaced it would leave nothing to go back to.

## Section 1: the vault, further

### 1.1 Aliases

- [ ] **Steps:** on a message that has your bookmark, ask Claude to `share` it to its list (or bookmark the same message from Claude's side with a different label). Open the note in Obsidian.
- [ ] **Expected:** `aliases` lists Claude's label; Obsidian's quick switcher (Ctrl+O) finds the note by either name.

### 1.2 Obsidian's stale buffer

- [ ] **Steps:** keep the note open in Obsidian's editor; relabel the bookmark from Claude Code (the plugin rewrites the note).
- [ ] **Expected:** Obsidian reloads the note (it watches the folder); if you had unsaved typing in it, Obsidian may keep yours -- then save and relabel once more: the plugin reads your version back (HV.3). Note what you saw: a documented limit, not a defect, unless an edit was lost without Obsidian saying so.

### 1.3 A hand-written `tags: a, b`

- [ ] **Steps:** in a text editor (not Obsidian), change a 0.5.9 note's `tags:` block to one line `tags: one, two`; relabel from Claude Code.
- [ ] **Expected:** the record's tags become `["one", "two"]`; the note is rewritten in list form.

## What the automated tests DO cover

| Area | Test file | Count |
|---|---|---|
| the primary record, aliases, derived tags, owners | `tests/core/note.test.ts` | 1 |
| the note's lists, version 2, reserved names | `tests/core/note.test.ts`, `tests/core/record.test.ts` | 2 |
| the YAML subset (block, flow, quotes, CRLF, nested, whitespace keys, empty items) | `tests/core/note.test.ts` | 1 |
| the ingest guard (floor, absent fields, base, `bm/*` stripped, comma scalars) | `tests/core/note.test.ts` | 1 |
| the base and the `noteBase` operation | `tests/core/note.test.ts` | 1 |
| read-back through the handler, before the action; an old note not read | `plugin/tests/note.test.ts` | 2 |
| `.bak` untouched by the bookkeeping write | `plugin/tests/guard.test.ts` | 2 |

## What the automated tests DON'T cover

- Obsidian's own parsing of the YAML, its properties pane, its tag pane and quick switcher (HV.2, 1.1)
- Obsidian's file watching and stale-buffer behaviour while the plugin rewrites a note (1.2)
- a real relabel from Claude's tool in a live session, with the real transcript resolved for the message text
- the debug log's lines as a person reads them
- the feel of it: whether editing a label in the vault and seeing it in the pane is obvious enough to be used

## Reporting issues found

1. Note the step (HV.n or n.m) and what you saw against what was expected.
2. Keep the note file and the bookmark file (`<sid>.json`, `.bak`) as they were at that moment.
3. File an issue referencing this checklist and the version; attach the log lines starting `[bm] note:`.
