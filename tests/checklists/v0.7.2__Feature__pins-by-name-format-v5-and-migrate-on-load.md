# Human Test Checklist: pins by name (register format v5) and migrate on load

**Target version:** 0.7.2
**Ships with commit:** `feat(bookmarks): pins by one name; register format v5, migrated on load (v0.7.2)` (subject may change at review)
**Companion automated tests:**
- core (`node --test tests/core/*.test.ts`), 539 in all. `tests/core/pins.test.ts` holds 17: pins, the scope, the union, each format version written in its own shape, the round trip at v2 to v5, and the steps v3 to v4 and v4 to v5.
- kit (`claude plugin test plugin`), 162 in all:
  - `plugin/tests/migrate-on-load.test.ts`, 4: a first load migrates with no start; a second load does nothing; a torn file with an older `.bak` is left alone; a failed migration leaves the file as it was and refuses a save;
  - `plugin/tests/pins.test.ts`, 3: `*2` writes a pin from the prompts list; the `here` and `everywhere` values of "Pins shown in a list".

**This supersedes the file details of `v0.7.1__Feature__pins-as-stars-and-format-v4.md`.** 0.7.1 wrote each pin record under the file key `stars` (format v4); from 0.7.2 the same record is written under `pins` (format v5). The screen is unchanged.

## What this is

0.7.2 does two things to the bookmark file:
1. **One name.** Pins are called pins in the file, in the code and in the setting's key (`pinScope`); the `/config` row is still "Pins shown in a list". A v4 file's `stars` list becomes a v5 file's `pins` list.
2. **Migrate on load.** A file older than the build is brought up to date, with a backup, the first time the build loads it, not only at a session's start. A file that cannot be brought up to date is shown but never written.

This checklist is for the maintainer, once per machine that has bookmarks.

## Legend

| Term | Meaning |
|---|---|
| register | the per-conversation bookmark file, `<data root>/bookmarks/sessions/<session id>.json` |
| data root | `CLAUDE_USER_DIR` when it is set, else `<home>/claude` |
| v3, v4, v5 | the register's `version` (and `format`) field. v3 held pins as a map under `pins` (owner to uuids); v4 held pin records under `stars`; v5 holds the same records under `pins` |
| pin record | `{uuid, owner, from, at}` plus `off` when the pin is turned off; `from` is the list it was made in (`prompts` for the prompts list) |
| run folder | one migration's backup folder under `<data root>/bookmarks/backups/`, named `<stamp>__v<from>-to-v<to>__<writer>__<first 8 of the session id>/`, holding the original file, its `.bak` and a `manifest.json` |
| start-up sweep | at a session's start, every register in the folder is migrated. A plugin reload also runs it |
| migrate on load | a session's own register is migrated the first time the build loads it, whatever the order of reload and start |

## Prerequisites

1. Claude Code with the plugin at 0.7.2 (`/bm-env` names the version).
2. **Run the migration sections on a copy, never on your real folder.** On a machine that already ran 0.7.2, every register is at v5. The v3 and v4 originals are in your run folders: `*__v3-to-v4__*` holds v3 files, `*__v4-to-v5__*` holds v4 files. Copy one into a scratch data root and start a fresh session there. `<RUN>` is a run folder's name, `<SID>` its session id.

   **cmd.exe**:
   ```cmd
   mkdir %TEMP%\bm-check-v5\claude\bookmarks\sessions
   copy "%USERPROFILE%\claude\bookmarks\backups\<RUN>\sessions\<SID>.json" %TEMP%\bm-check-v5\claude\bookmarks\sessions\
   set CLAUDE_USER_DIR=%TEMP%\bm-check-v5\claude
   claude
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\bm-check-v5\claude\bookmarks\sessions" | Out-Null
   Copy-Item "$env:USERPROFILE\claude\bookmarks\backups\<RUN>\sessions\<SID>.json" "$env:TEMP\bm-check-v5\claude\bookmarks\sessions\"
   $env:CLAUDE_USER_DIR = "$env:TEMP\bm-check-v5\claude"
   claude
   ```

   **POSIX**:
   ```bash
   mkdir -p /tmp/bm-check-v5/claude/bookmarks/sessions
   cp "$HOME/claude/bookmarks/backups/<RUN>/sessions/<SID>.json" /tmp/bm-check-v5/claude/bookmarks/sessions/
   export CLAUDE_USER_DIR=/tmp/bm-check-v5/claude
   claude
   ```

   A run folder whose original has pins:

   **PowerShell**: `Select-String -Path "$env:USERPROFILE\claude\bookmarks\backups\*__v4-to-v5__*\sessions\*.json" -Pattern '"stars"' -List | Select-Object Path`

   **POSIX**: `grep -l '"stars"' "$HOME"/claude/bookmarks/backups/*__v4-to-v5__*/sessions/*.json`

   **cmd.exe**: `findstr /m /s "\"stars\"" "%USERPROFILE%\claude\bookmarks\backups\*.json"`

   (For a v3 original, use `*__v3-to-v4__*` and the pattern `"pins"`.)
3. **Reset between sections:** delete the scratch folder and copy again.

## High-Value Verification (~5 minutes)

### HV.1: a v4 register becomes v5, its pins under `pins`

Validates: the v4-to-v5 step, through the start-up sweep and migrate on load.

- [ ] **Steps:** start a session on the scratch root holding a v4 original (Prerequisites, step 2), open the prompts pane (`Ctrl+] p`), then open the register:
  - **PowerShell**: `Get-Content "$env:CLAUDE_USER_DIR\bookmarks\sessions\<SID>.json"`
  - **cmd.exe**: `type %CLAUDE_USER_DIR%\bookmarks\sessions\<SID>.json`
  - **POSIX**: `cat "$CLAUDE_USER_DIR/bookmarks/sessions/<SID>.json"`
- [ ] **Expected:**
  - `"version": 5` and `"format": 5`;
  - a `"pins"` list with the same records the original held under `"stars"`, each with `"from": "prompts"`;
  - no `"stars"` key;
  - the bookmarks (`"perma"`) and the letters (`"slots"`) unchanged.
- [ ] **Why this matters:** a pin lost in a rename is a pin lost from the person's list.

### HV.2: a v3 register goes the whole way, v3 to v5 in one run

- [ ] **Steps:** as HV.1, with a v3 original (from a `*__v3-to-v4__*` run folder).
- [ ] **Expected:** one run folder named `__v3-to-v5__`, whose `manifest.json` says `"status": "done"`, `"from": 3`, `"to": 5`. The file is as in HV.1, with each pin of the old map now a record under `"pins"`.
- [ ] **Why this matters:** this is a machine that never ran 0.7.1.

### HV.3: the backup is the original

- [ ] **Steps:** compare the run folder's `sessions/<SID>.json` with the file you copied in: `fc /b a b` (cmd.exe), `Compare-Object (Get-Content a) (Get-Content b)` (PowerShell), `cmp a b` (POSIX).
- [ ] **Expected:** identical.
- [ ] **Why this matters:** the backup is the only way back.

### HV.4: the prompts pane and pinning, after the migration

- [ ] **Steps:** on your real data root (no `CLAUDE_USER_DIR`), in a conversation that had pins, press `Ctrl+] p`; then `*N` and Enter in the pane's field (from `/bm-prompts` with an empty input box) on an unpinned prompt, and again.
- [ ] **Expected:** the **★ pinned** group as before; the first toggle pins (toast "pinned #N"), the second unpins ("unpinned #N"). In the register the record is under `"pins"`, and gains an `"off"` time on unpin.
- [ ] **Why this matters:** the screen must be exactly as before the rename.

### HV.5: the setting and `/bm-check`

- [ ] **Steps:** `/config`, the Bookmarks fold; then `/bm-check`.
- [ ] **Expected:** "Pins shown in a list", `here` and `everywhere`, set to `here`. `/bm-check` reports every register at v5 with no warning about them. (The setting's key changed from `starScope` to `pinScope`. A value saved under the old key would read as the default, `here`; none is expected, since 0.7.1 shipped the setting the same day.)

## Section 1: the folder

### 1.1 One sweep migrates every register

- [ ] **Steps:** copy several originals, v3 and v4 mixed, into the scratch `sessions/`, then start one session.
- [ ] **Expected:** every file at v5, one run folder each (`__v3-to-v5__` or `__v4-to-v5__`).

### 1.2 Nothing more on a second start, or a second load

- [ ] **Steps:** close the session and start another on the same root; open the prompts pane twice.
- [ ] **Expected:** no new run folder; the register's `rev` is unchanged by the start.

## Section 2: when a migration cannot run (optional, manual)

These need a state a person seldom has. They are covered by kit tests; run them only to see the wording.

### 2.1 A file that cannot be written

- [ ] **Steps:** in the scratch root, make the copied register read-only in the file system before starting the session (`attrib +r <file>` on cmd.exe; `Set-ItemProperty <file> -Name IsReadOnly -Value $true` in PowerShell; `chmod a-w <file>` on POSIX), start, open the prompts pane, try `*1`.
- [ ] **Expected:**
  - a toast "this conversation's bookmark file could not be brought up to date; it is read-only for now (see /bm-check)";
  - the pin is refused with "not saved: ... could not be brought up to date ...";
  - the register is unchanged;
  - a run folder is left with its manifest at `"status": "backed-up"`: the copies were made before the write failed. `/bm-check` names it.

  Clear the attribute afterwards. The next start then migrates the file.

### 2.2 A torn file with an older `.bak`

- [ ] **Steps:** in the scratch `sessions/`, put the v4 original as `<SID>.json.bak`, and the first half of it as `<SID>.json`; start.
- [ ] **Expected:** neither file changes and no run folder appears; the read-only toast as in 2.1. (Migrating from the `.bak` would copy the torn text over the good backup.)

## Section 3: across machines and builds

### 3.1 A second machine's first start on 0.7.2

- [ ] **Steps:** update the plugin there and start a session.
- [ ] **Expected:** HV.1 to HV.3 on that machine's own folder; v3 files go to v5 in one run folder each.

### 3.2 An older build meets a v5 file

Run only where an older build is installed.

- [ ] **Steps:** with 0.7.1 or older, open a conversation whose register is at v5; try to pin.
- [ ] **Expected:** a toast at load, "written by a newer build ... read-only here until the plugin is updated"; nothing is saved, and the file is unchanged. Its pins do not show, because that build reads `stars` or the old map.

## What the automated tests DON'T cover

- A real folder with real files, `.bak`s and timestamps (Sections 1 and 3).
- A plugin reload in a live session: the kit always starts its sessions. A reload also runs the start-up sweep, which only a live session shows.
- A file the operating system will not let the plugin write (Section 2.1); the kit fakes it with a failing write.
- The toasts' wording and how long they stay.
- An older build on another machine (Section 3.2).

## Reporting issues found

1. Note the section and step.
2. Keep the scratch folder as it is, and copy the run folder and the register.
3. File an issue naming this checklist and the version from `/bm-env`.

## Cleanup

Clear any read-only attribute you set, delete the scratch data root and unset `CLAUDE_USER_DIR`:

- **cmd.exe**: `rmdir /s /q %TEMP%\bm-check-v5` then `set CLAUDE_USER_DIR=`
- **PowerShell**: `Remove-Item -Recurse -Force "$env:TEMP\bm-check-v5"` then `Remove-Item Env:\CLAUDE_USER_DIR`
- **POSIX**: `rm -rf /tmp/bm-check-v5` then `unset CLAUDE_USER_DIR`

Your real folder is touched only by HV.4 and HV.5, by an ordinary pin you can undo by toggling again.
