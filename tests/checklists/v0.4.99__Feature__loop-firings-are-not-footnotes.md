# Human Test Checklist: loop firings are not footnotes; long footnote labels are cut

**Target version:** 0.4.99
**Ships with commit:** fix(prompts): a /loop firing is not the person's footnote; labels cut to 120 (v0.4.99)
**Companion automated tests:** `tests/core/prompt-rows.test.ts` (2 new: a scheduled firing is neither prompt nor footnote; a label is cut to 120 with "…"), `plugin/tests/seams.test.ts` (2 new: a scheduled firing is not kept as a footnote by its origin, and its control). The core tests failed on the code before the fix; the kit test failed on a copy of the plugin without the new guard.

## What this is

What a person checks by hand after upgrading to 0.4.99: that a running `/loop` stops adding footnotes to the prompts list, that the footnotes already stored from loop firings are gone after the first start, that the person's own slash commands, `!` shell commands and interruptions still show as footnotes, and that a footnote with a very long label draws on one row. The tests cover the rules; only a real session shows the live firing's origin and the re-read of real transcripts.

## Prerequisites

1. Claude Code 2.1.287 or later, fullscreen renderer, the plugin at 0.4.99 (`/bm-env` shows the version).
2. **Back up the plugin store before upgrading** -- copy it, never edit it by hand:

   **cmd.exe**:
   ```cmd
   mkdir %USERPROFILE%\claude\backups\plugin-store
   copy %USERPROFILE%\.claude\plugins\store\bookmarks_inline-*.json %USERPROFILE%\claude\backups\plugin-store\
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:USERPROFILE\claude\backups\plugin-store" | Out-Null
   Copy-Item "$env:USERPROFILE\.claude\plugins\store\bookmarks_inline-*.json" "$env:USERPROFILE\claude\backups\plugin-store\"
   ```

   **POSIX**:
   ```bash
   mkdir -p ~/claude/backups/plugin-store
   cp ~/.claude/plugins/store/bookmarks_inline-*.json ~/claude/backups/plugin-store/
   ```
3. For HV.4, `jq` or Python. Measure a **copy** of the store, never the live file while Claude Code runs.
4. Turn the debug echo on in the conversation you test: `/bm-debug on`.

## High-Value Verification (~5 minutes)

### HV.1 -- A running /loop adds no footnotes

Validates: the live capture refuses a row the schedule caused (its `origin.kind`; assumed `scheduled-trigger`, not yet seen live).

- [ ] **Steps:**
  1. In a conversation, start a loop that runs a slash command often, for example `/loop 1m /bm-env`.
  2. Open the prompts list (leader, `p`), note the last prompt's footnote count (`… N footnotes` under it, or none).
  3. Let the loop fire three times; reopen the list.
- [ ] **Expected:** the footnote count under the last prompt has not grown. Stop the loop.
- [ ] **Why this matters:** before 0.4.99 every firing added a footnote; one conversation kept 337 of them, most of the plugin store.

### HV.2 -- Stored firings are gone after the first start

Validates: the back-fill's version 7 re-reads each conversation and rewrites its footnotes without firings.

- [ ] **Steps:**
  1. Resume a conversation that ran a `/loop` before 0.4.99 (`claude --resume`).
  2. Open the prompts list and unfold a prompt the loop ran under (`N.` in the list's field).
- [ ] **Expected:** no footnote rows for the loop's command; the debug log has one back-fill line for this conversation (`[bm] backfill: ...`).
- [ ] **Why this matters:** the fix must also clean what was already stored, not only stop new firings.

### HV.3 -- The person's own footnotes still show

Validates: the refusal is by who caused the row, not by what it says.

- [ ] **Steps:**
  1. Type a slash command yourself (`/bm-env`), a shell command (`!echo hi`), and send a prompt, then press Esc while Claude answers.
  2. Open the prompts list and unfold the prompts before them.
- [ ] **Expected:** a `/bm-env` footnote, a `!echo hi` footnote, and an interruption footnote, each under the prompt before it.
- [ ] **Why this matters:** a filter on the command's text would have dropped the person's own `/bm-env` too.

### HV.4 -- The store is smaller

Validates: the cleanup reached the store file.

- [ ] **Steps** (on a fresh copy taken after HV.2's start):

  **PowerShell**:
  ```powershell
  Copy-Item "$env:USERPROFILE\.claude\plugins\store\bookmarks_inline-*.json" "$env:TEMP\store-after.json"
  jq '[to_entries[] | select(.key|startswith("footnotes:")) | .value[]] | length' "$env:TEMP\store-after.json"
  ```

  **cmd.exe**:
  ```cmd
  copy %USERPROFILE%\.claude\plugins\store\bookmarks_inline-*.json %TEMP%\store-after.json
  jq "[to_entries[] | select(.key|startswith(\"footnotes:\")) | .value[]] | length" %TEMP%\store-after.json
  ```

  **POSIX**:
  ```bash
  cp ~/.claude/plugins/store/bookmarks_inline-*.json /tmp/store-after.json
  jq '[to_entries[] | select(.key|startswith("footnotes:")) | .value[]] | length' /tmp/store-after.json
  ```
- [ ] **Expected:** fewer footnotes than before, once every conversation that ran a loop has been reopened (the author's store before: 671 footnotes, 848,286 bytes in the footnotes family). A conversation not reopened keeps its old footnotes until it is.
- [ ] **Why this matters:** the store counts against Claude Code's 4 MiB limit for a plugin's store.

### HV.5 -- A long footnote label draws on one row

- [ ] **Steps:** run a slash command with long arguments (paste a few hundred characters after `/bm-env `, or find a `/goal` with its brief), open the list and unfold its prompt.
- [ ] **Expected:** the footnote shows the command and the start of its arguments on one row, ending in "…".

## What the automated tests DO cover

| Area | Test file | Count |
|---|---|---|
| A scheduled row is neither prompt nor footnote; the same command typed is a footnote | `tests/core/prompt-rows.test.ts` | 1 |
| The label cut at 120 with "…"; short labels untouched | `tests/core/prompt-rows.test.ts` | 1 |
| The live capture keeps no footnote for a `scheduled-trigger` origin; the person's is kept | `plugin/tests/seams.test.ts` | 2 |

## What the automated tests DON'T cover

- The `origin.kind` a real `/loop` firing arrives with (HV.1).
- The re-read of real transcripts at a real start, and the store file afterwards (HV.2, HV.4).
- How a cut label reads in a narrow or wide pane (HV.5).

## Reporting issues found

Note the HV number, the conversation's id (`/bm-env`), and the debug log lines around it (`~/claude/bookmarks/debug/<session id>.log`); file an issue citing this checklist and 0.4.99.

## Cleanup

Stop any `/loop` you started (HV.1) and `/bm-debug off`. To go back to the store as it was, quit Claude Code and copy the backup from the prerequisites over the live file.
