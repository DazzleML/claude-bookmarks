# Human Test Checklist: The plugin is `bookmarks` and lives in `plugin/` (v0.3.0)

**Target version:** 0.3.0
**Ships with commit:** v0.3.0: the plugin is `bookmarks`, in its own folder, installable from this repository (TBD at commit)
**Ships after:** v0.2.2, `5b44c03`
**Companion automated tests:** 32 under `plugin/hooks/core/` (`node --test plugin/hooks/core/anchor.test.ts plugin/hooks/core/transcript-lines.test.ts plugin/hooks/core/register-file.test.ts`), 37 exploratory under `tests/one-offs/thinking/anchors/`, 9 in `tests/test_version.py` (the manifest's version and name). `npx tsc -p plugin --noEmit`, `claude plugin validate ./plugin` and `claude plugin validate .` must all pass. The two PowerShell scripts were compared with `grep` on a 4 MB transcript before the commit: the same 19 user rows, the same 25 matches with the same byte offsets.

## What this is

v0.3.0 changes no behaviour on purpose and changes three things around the behaviour: the plugin's name (`convo-bookmarks` becomes `bookmarks`, published by DazzleML), where it lives (the repository's `plugin/` folder, so an install carries the plugin and not the repository's tests and tooling), and how it reads the transcript on Windows (two PowerShell scripts shipped with the plugin, run by file, in place of base64-encoded inline commands). Each of those is a way to break a working install silently: a wrong path loads nothing, a renamed store loses every mark, a script that differs from `grep` by one byte breaks every bookmark link. This checklist is the proof that none of that happened on a real machine. Its live steps need the person's own sessions and settings; no agent can run them.

## Prerequisites

1. Claude Code 2.1.295 or later. Windows is the tested platform; the PowerShell steps are Windows-only by nature.
2. A clone of the repository at v0.3.0 or later. Below, `<repo>` is its path.
3. **Before changing anything, back up the plugin store** (it holds every conversation's marks, pins, reading positions, prompt lists and jumplists):

   **cmd.exe**:
   ```cmd
   copy "%USERPROFILE%\.claude\plugins\store\convo-bookmarks_inline-*.json" "%TEMP%\"
   ```

   **PowerShell**:
   ```powershell
   Copy-Item "$env:USERPROFILE\.claude\plugins\store\convo-bookmarks_inline-*.json" $env:TEMP
   ```

   **POSIX**:
   ```bash
   cp ~/.claude/plugins/store/convo-bookmarks_inline-*.json /tmp/
   ```

4. The marketplace install step uses a throwaway config dir (`CLAUDE_CONFIG_DIR`) so it cannot touch your settings; the steps say so where it applies.
5. Reset between sections: nothing destructive happens except the store merge (HV.3), which keeps a `.bak` beside the new file.

## High-Value Verification (~10 minutes)

### HV.1 — The plugin loads from `plugin/` under its new name

Validates: the manifest, hooks and types resolve at the new paths; the name is `bookmarks`.

- [ ] **Steps:**
  1. In `~/.claude/settings.json`, change the `env` block's `CLAUDE_CODE_PLUGIN_DIRS` from `<repo>` to `<repo>\plugin` (POSIX: `<repo>/plugin`). Keep a copy of the old value.
  2. Start a new Claude Code session from a shell (not a daemon-hosted one), fullscreen renderer.
  3. `/bm-env`
- [ ] **Expected:** the band appears above the prompt; `/bm-env` prints `bookmarks 0.3.0 on Claude Code 2.1.29x …`. No line mentions `convo-bookmarks`.
- [ ] **Why this matters:** a wrong path or a broken manifest loads nothing, silently.

### HV.2 — Claude's tool has the new id

Validates: the regex hook matcher answers `mcp__bookmarks__bookmark`.

- [ ] **Steps:** in that session ask Claude to "bookmark the message where I said <some words you typed earlier> and give me the link".
- [ ] **Expected:** Claude calls a tool shown as `mcp__bookmarks__bookmark`, the reply carries a `⚓` link, and a plain click jumps there with the words highlighted.
- [ ] **Why this matters:** the matcher is the one place the plugin's name is still spelled out in code.

### HV.3 — Marks, pins and the reading position come back after the store merge

Validates: the one-time merge of the old store file into the new one.

- [ ] **Steps:**
  1. In the new session, `Ctrl+] '` (the jump pane): expect it empty or nearly so; your old marks are in the old store file.
  2. Close every Claude Code session that still runs the old plugin (ones started before step HV.1).
  3. Dry run, then apply (same in every shell):
     ```
     python tests/one-offs/thinking/store-migration/migrate_store.py
     python tests/one-offs/thinking/store-migration/migrate_store.py --apply
     ```
  4. Restart the session from HV.1 (`claude --resume <its id>`), then `Ctrl+] '` and `Ctrl+] p`.
- [ ] **Expected:** the dry run names one old file and one new file and lists the key kinds it would copy (`marks`, `pins`, `prompts`, `jumplist`, `readingBack`, `debug`, …); after `--apply` a `.bak` of the new file exists beside it; the resumed session's jump pane lists the marks that conversation had, the prompts pane its pins.
- [ ] **Why this matters:** the store is named after the plugin; without the merge every mark on the machine is orphaned in the old file.

### HV.4 — The repository installs as a marketplace

Validates: `.claude-plugin/marketplace.json` and the `./plugin` source.

- [ ] **Steps** (a throwaway config dir, so nothing of yours is touched):

  **cmd.exe**:
  ```cmd
  set CLAUDE_CONFIG_DIR=%TEMP%\bm-install-test
  claude
  ```

  **PowerShell**:
  ```powershell
  $env:CLAUDE_CONFIG_DIR = "$env:TEMP\bm-install-test"
  claude
  ```

  **POSIX**:
  ```bash
  CLAUDE_CONFIG_DIR=/tmp/bm-install-test claude
  ```

  Then, inside: `/plugin marketplace add DazzleML/claude-bookmarks`, `/plugin install bookmarks@dazzle-claude-plugins` (or `/plugin install bookmarks --marketplace DazzleML/claude-bookmarks`), restart that session, `/bm-env`.
- [ ] **Expected:** the install succeeds from the `plugin/` folder; `/bm-env` prints `bookmarks 0.3.0`. Afterwards delete the throwaway dir (cmd `rmdir /s /q "%TEMP%\bm-install-test"`; PowerShell `Remove-Item -Recurse "$env:TEMP\bm-install-test"`; POSIX `rm -rf /tmp/bm-install-test`), or `dz safedel` it.
- [ ] **Why this matters:** this is the install line both READMEs now give.

### HV.5 — The PowerShell fallbacks agree with grep

Validates: the two `.ps1` scripts the mod runs on Windows when `sh` and `grep` are absent.

- [ ] **Steps** (Windows; from the repository root; `<jsonl>` is a copy of any transcript under `%USERPROFILE%\.claude\projects\…`):

  **PowerShell**:
  ```powershell
  powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -File plugin\hooks\scripts\user-rows.ps1 -Path <jsonl> -UserRow '"type":"user"' -ToolResultRow '"type":"tool_result"' | Measure-Object -Line
  powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -File plugin\hooks\scripts\grep-offsets.ps1 -Path <jsonl> -Pattern '"type":"user"' | Select-Object -First 1
  ```

  **POSIX (Git Bash), the reference**:
  ```bash
  grep -F '"type":"user"' <jsonl> | grep -vF '"type":"tool_result"' | wc -l
  grep -bnF -- '"type":"user"' <jsonl> | head -1
  ```
- [ ] **Expected:** the same row count from both; the first `grep-offsets` line equals `grep -bn`'s first line, `<line>:<byteoffset>:…`.
- [ ] **Why this matters:** a byte offset off by one breaks every bookmark link minted on a machine without `grep`.

- [ ] **Steps:** once no session still runs the plugin from the repository root, remove `<repo>/.claude-plugin/types/` (`dz safedel <repo>/.claude-plugin/types` where available). It is git-ignored and regenerated by the engine under `plugin/.claude-plugin/types/`.

## What the automated tests DON'T cover

- That Claude Code loads the plugin from the new folder (HV.1) and under the new name (HV.2).
- The store merge on a real machine (HV.3); the script's dry run was exercised against a real old store and a fresh new one before the commit.
- The marketplace install (HV.4): network, `git`, the directory's own checks.
- The PowerShell scripts as the mod invokes them (HV.5); the pre-commit comparison ran them the same way from a test harness.
- The engine regenerating its types under `plugin/` (1.3).

## Reporting issues found
